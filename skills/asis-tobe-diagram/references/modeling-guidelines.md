# Modeling Guidelines

## 1. 正本

`process-model.json` を意味情報の正本とする。HTML、SVG、PNG、PDFは派生成果物であり、更新はJSONに対して行う。

## 2. モデルの層

| 層 | 主な要素 | 目的 |
|---|---|---|
| 文書管理 | `meta`, `schemaVersion`, `view` | 目的、範囲、版、根拠、表示条件 |
| 業務構造 | `states`, `lanes`, `stages`, `nodes`, `edges` | As-is / To-beの実体 |
| 改善論理 | `painPoints`, `changes`, `objectives`, `kpis` | 課題から変更、効果への追跡 |
| 実装・運用 | `risks`, `openQuestions`, `implementation` | 実現性、移行、運用責任 |

## 3. ID規約

IDは短く、安定し、意味変更がない限り維持する。

| 種別 | 例 |
|---|---|
| As-is node | `A-01` |
| To-be node | `T-01` |
| As-is edge | `AE-01` |
| To-be edge | `TE-01` |
| Pain point | `P-01` |
| Change | `C-01` |
| KPI | `K-01` |
| Risk | `R-01` |
| Open question | `Q-01` |
| Objective | `O-01` |
| Source | `S-01` |
| Assumption | `AS-01` |

表示順の変更だけでIDを振り直さない。削除したIDを別の意味で再利用しない。

## 4. レーンと工程

- **lane** は責任主体またはシステム境界を表す。
- **stage** は時系列またはライフサイクル上の工程を表す。
- 役割と個人名を混在させない。原則として役割名を使う。
- As-isとTo-beで比較可能な概念は同じlane ID、stage IDを使ってよい。
- 組織改編そのものが変更点の場合は、新旧のレーンを分け、`changes`で関係を示す。

## 5. ノード

ノード名は原則「動詞＋目的語」。例: `申請内容を確認する`。

| `type` | 用途 |
|---|---|
| `start` / `end` | 明示的な開始・終了 |
| `activity` | 人または組織の処理 |
| `decision` | 条件による分岐 |
| `system` | システム処理・サービス呼出し |
| `data` | データストア、マスタ、キュー |
| `document` | 帳票、申請書、CSV、通知 |
| `control` | 承認、照合、監査、権限確認 |
| `external` | 顧客、取引先、外部サービスとの接点 |
| `milestone` | 業務上の確定点、締め、SLA境界 |
| `note` | 図上の補足。処理として扱わない |

### ノードに最低限持たせる情報

- `id`, `label`, `type`, `lane`, `stage`
- `mode`: `manual`, `automated`, `hybrid`, `unknown`
- 根拠がある場合は `sourceIds`
- 未確定なら `status` と `confidence`
- 課題、変更、リスクがある場合は対応ID

1ノードに複数の独立した業務判断や処理を詰め込まない。詳細が大きい場合はサブプロセスとして分割する。

## 6. エッジ

| `type` | 意味 |
|---|---|
| `sequence` | 通常の処理順 |
| `data` | データ参照・受渡し |
| `integration` | システム間連携 |
| `exception` | 例外、失敗、差戻し |
| `control` | 承認、照合、統制上の関係 |
| `manual-handoff` | 人・組織間の手渡し、メール、電話等 |

判断ノードから出る線には、可能な限り条件ラベルを付ける。戻り線、例外線、データ線を通常フローと同じ意味で描かない。

## 7. 課題

課題は感想ではなく、観測可能な状態として書く。

悪い例: `非効率`
良い例: `申請内容を基幹システムへ再入力しており、転記ミスと処理待ちが発生する`

各課題は次を持つことが望ましい。

- 発生箇所（nodeまたはedge）
- 症状、原因、影響
- 頻度または規模。未計測ならその旨
- 根拠 `sourceIds`
- 優先度または重大度

## 8. 変更

To-be変更は、少なくとも1つの課題または目的に紐付ける。変更には次を含める。

- 何を廃止、追加、統合、自動化、移管するか
- As-isの対象IDとTo-beの対象ID
- 解決対象の `painPointIds` または `objectiveIds`
- 実現条件、依存、採用状態
- 失敗時の代替手段

技術名だけの変更にしない。`AIを導入する` ではなく、対象判断、入力、出力、検証、例外処理、責任を表す。

## 9. KPI

KPIは変更の効果または運用品質を測る。少なくとも次を明示する。

- 定義と除外条件
- ベースライン。なければ `未計測`
- 目標。暫定なら `仮目標`
- 算式または測定方法
- データソース
- 責任者と測定頻度
- `changeIds`

効率KPIだけでなく、品質、統制、信頼性のガードレールを組み合わせる。

## 10. 根拠・仮定・矛盾

- 観測事実は `meta.sources` と各要素の `sourceIds` で追跡する。
- 推定は `meta.assumptions` に分離する。
- 情報源間の不一致は `meta.conflicts` に記録する。
- 不明事項は `openQuestions` にし、回答者、期限、影響範囲を付ける。
- 根拠がない数値を見栄えのために作らない。

## 11. 自動化・AI・RPA

最低限、次を図に出す。

1. トリガー
2. 入力検証
3. 自動処理
4. 成功判定
5. 例外キューまたは人への引継ぎ
6. 再実行または手動フォールバック
7. 業務完了確認
8. 運用責任者

`references/automation-and-agentic-design.md` も併用する。

## 12. 粒度

- 経営合意: 主要レーン、主要工程、課題、変更、KPI
- 業務合意: 通常フロー、主要例外、責任、システム、統制
- 要件定義: 入出力、判断条件、例外、データ、連携、運用
- 実装設計: 本スキルの概要図とは別に、BPMN、シーケンス、データモデル等へ展開

各状態35ノードを超える場合は、概要と詳細に分けることを優先する。

## 13. バージョン管理

- 文言修正・小規模内容変更: patch
- 要素追加、構造変更、比較軸変更: minor
- スキーマ互換性を壊す変更: major

`meta.updatedAt` と `meta.changeLog` を更新し、IDベースの差分を保存する。
